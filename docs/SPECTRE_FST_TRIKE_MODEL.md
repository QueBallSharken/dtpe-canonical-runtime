# SPECTRE-FST TRIKE MODEL (LOCKED)

PURPOSE

This document locks the current high-level architecture framing for the DTPE / IAL / SPECTRE core, GDP sidecar, and SPECTRE-FST plus Upgrade Analysis third-wheel direction.

It exists to preserve role separation, prevent future subsystem collapse, and provide a stable architecture anchor before broader docs realignment.

This artifact is architecture framing only.

It does not claim runtime implementation of SPECTRE-FST.
It does not claim GDP performs runtime execution proof.
It does not normalize future Sentinel work into the current active runtime direction.

---

## 1. TRIKE MODEL

The architecture is framed as a trike with three distinct structural roles:

1. DTPE / IAL / SPECTRE
2. GDP
3. SPECTRE-FST plus Upgrade Analysis

These roles must remain separate.

---

## 2. DTPE / IAL / SPECTRE

DTPE / IAL / SPECTRE is the core governed execution and proof engine.

Its role is to:

- bind canonical governance inputs
- evaluate execution-bound governance conditions
- produce receipt-bearing execution evidence
- support replay-verifiable proof of what governed execution actually did

DTPE / IAL / SPECTRE is the core frame of the system.

It is not the structural sufficiency sidecar.
It is not the fundamental stress testing subsystem.
It is not the upgrade analysis subsystem.

---

## 3. GDP

GDP is the structural sufficiency sidecar.

Its role is to evaluate whether a governance model is structurally sufficient in principle.

GDP answers questions such as:

- is the governance model structurally complete
- are the claimed controls present in model form
- does the architecture described by the target appear sufficient on its own terms

GDP does not itself prove runtime execution truth.

GDP does not itself produce canonical execution proof.

GDP remains separate from DTPE execution-bound proof.

---

## 4. GDP BRIDGE POSITION

The GDP bridge is the comparison layer between GDP structural claims and DTPE proof summary / artifact-backed evidence.

Its role is to determine whether DTPE proof:

- matches GDP structural claims
- is insufficient for GDP structural claims
- contradicts GDP structural claims

Preferred language:

- GDP evaluates structural sufficiency
- DTPE / IAL / SPECTRE substantiate execution proof
- the bridge determines whether DTPE proof matches, is insufficient for, or contradicts GDP structural claims

The bridge does not collapse GDP into DTPE.
The bridge does not turn GDP into runtime execution.
The bridge does not elevate structural sufficiency into execution truth.

---

## 5. SPECTRE-FST

SPECTRE-FST is the bounded fundamental stress evaluation subsystem.

Its role is to stress-test whether claimed governing truth survives distinct deformation classes.

SPECTRE-FST is not the DTPE execution-bound evaluator.
SPECTRE-FST is not GDP structural sufficiency evaluation.
SPECTRE-FST is not free-form commentary.

SPECTRE-FST must remain bounded.

That boundedness includes:

- fixed stress categories
- multiple bounded outcomes per category
- fixed evaluator rule profile
- deterministic receipt shape
- explicit findings / gaps / contradictions structure

SPECTRE-FST exists to evaluate whether architecture claims survive pressure, not merely whether they sound complete on paper.

---

## 6. UPGRADE ANALYSIS

Upgrade Analysis is the evidence-grounded hardening layer derived from SPECTRE-FST findings.

Its role is to map observed weaknesses to factual hardening recommendations.

Upgrade Analysis must remain downstream of stress findings.

It must not replace:
- stress evaluation
- receipt classification
- execution proof
- structural sufficiency evaluation

Upgrade Analysis should be grounded in:
- observed weak points
- stress findings
- identified gaps
- contradictions
- bounded architectural reasoning

It must not become generic best-practice output.

---

## 7. SELECTOR VS CANONICAL EVALUATOR

The adaptive weak-point selection function must remain separate from canonical stress evaluation.

Selector role:

- inspect architecture
- identify likely weak points
- choose relevant stress families
- produce bounded targeting rationale

Canonical evaluator role:

- run bounded stress categories
- produce deterministic outcome classification
- emit receipt-bearing findings, gaps, and contradictions

This split preserves:
- adaptive targeting
- deterministic evaluation
- replay-stable receipt meaning

Adaptive selection must not blur canonical evaluation.

---

## 8. STRESS CATEGORIES AND OUTCOMES

Each stress category has fixed identity but multiple bounded outcomes.

This means:

- stress category identity remains stable
- outcome may differ across different scenarios
- same exact canonical scenario with same exact evaluator rules must produce the same exact result

Category is fixed.
Outcome is case-dependent.
Meaning is bounded.

This prevents SPECTRE-FST from collapsing into either:
- static label stamping
- unconstrained free-form analysis

---

## 9. RECEIPT DIRECTION

SPECTRE-FST must be receipt-bearing.

A bounded SPECTRE-FST receipt direction includes at least:

- fst_profile_id
- fst_profile_version
- fst_rule_profile
- fst_rule_hash
- stress_scenario_id
- stress_class
- stress_input_hash
- fst_result
- fst_findings
- fst_gaps
- fst_contradictions

Upgrade Analysis may be attached as a downstream evidence-grounded hardening section, but must remain distinct from the stress result itself.

---

## 10. LOCKED WORKFLOW

The current locked workflow is:

Find it.
Fix it.
Map it.
Dock it.
Bound it.
Receipt-bind it.
Stress it.
Spec it.

This workflow must be interpreted strictly:

- Find it = identify the real blocker or weak point
- Fix it = remove or constrain the blocker before broad mapping
- Map it = define the structure
- Dock it = attach it to the architecture
- Bound it = constrain roles, categories, outcomes, and claims
- Receipt-bind it = make it evidence-bearing
- Stress it = pressure-test the bounded architecture
- Spec it = write stable normative language after the structure is disciplined
